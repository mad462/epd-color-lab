# 数据格式：48 色 / 单色快刷 是怎么组织的

> 这份讲**数据怎么排布**。颜色怎么测、怎么调看 [颜色方法论.md](颜色方法论.md)。

---

## 一、先记住三层的区别

同一张图，在三个地方尺寸完全不同：

```
① 逻辑层（网页发过来的）    8bpp 索引        345,600 字节
② 平面层（拆成两个 3bit）                          ×2
③ 线路层（真正推给面板的）   4bpp 帧         172,800 字节 / 次
```

**搞混这三层是最容易出错的地方**（我们就踩过：把 4bpp 的 172800 当成 8bpp 的长度传进去，面板直接报错）。

---

## 二、48 色：三层结构

### ① 逻辑层 —— 8bpp 索引缓冲

```
一像素一字节：  index = 高3位 × 8 + 低3位
尺寸：          720 × 480 = 345,600 字节
```

**这就是网页 `POST /raw` 发过来的东西**，也是 `- 02_qual_*.bmp` 里的像素数据。

- `index` 取值 0~63
- 但不是 64 个都有效：**只有 48 个有对应波形**（见第四节）

### ② 平面层 —— 拆成两个 3-bit 平面

```c
plane 0 = index >> 3     // 高 3 位，0~7
plane 1 = index & 7      // 低 3 位，0~7
```

**8 × 8 = 64 种组合。** 两个平面分两次写进控制器的两个 3bit 帧存。

### ③ 线路层 —— 每个平面编码成 4bpp

```c
// main/epd370.c:316
for (int y = 0; y < 480; y++) {
    const uint8_t *row = index8 + y * 720;
    uint8_t *out = s_plane + y * 360;
    for (int x = 0; x < 720; x += 2) {
        uint8_t a = row[x], b = row[x + 1];
        if (plane == 0) { a >>= 3; b >>= 3; }   // 高 3 位
        else            { a &= 7;  b &= 7;  }   // 低 3 位
        *out++ = (a << 4) | b;   // 高半字节 = 左（偶数 x）
    }                            // 低半字节 = 右（奇数 x）
}
```

```
一行：720 像素 × 4 bit = 360 字节
一帧：360 × 480      = 172,800 字节
```

## 三、48 色：刷新流程（3 次传输 + 3 个相位）

```
0) wf_full_clear       + 全 0 帧（172800 B）   刷新 ~2.5 s   清到已知起点
1) wf_qual_phase1      + plane0（172800 B）    刷新 ~5.6 s   写高 3 位
2) wf_qual_phase2      （复用 RAM，不重传）     刷新 ~6.5 s   中间显影
3) wf_qual_phase3      + plane1（172800 B）    刷新 ~0.1 s   写低 3 位
                                              ──────────
                                              合计 ~14.7 s
```

**一次完整刷新的 SPI 总量 = 3 × 172800 = 518,400 字节。**

> **这是理解一切的关键**：48 色不是靠位深堆出来的，是靠
> **「两个平面 × 三个相位」在时间上合成出来的**。
> 也解释了为什么 7.3″ 那块屏做不到 —— 它只有一个平面、且波形是饱和型
> （相位之间接续不起来），缺的正是这个能力。详见
> [面板对比_3.7_7.3_7.09.md](面板对比_3.7_7.3_7.09.md)。

## 四、为什么是 48 而不是 64

索引 0~63 里，**只有 48 个索引有对应的波形条目**。

剩下的是空条目（AI 硬改出来的"64 色色卡"之所以乱，就是因为它假设 64 个都有效）。

- 有效索引列表在 `host/act/palettes.json` 的 `active` 字段（52 项，其中 46 个颜色不重复）
- 固件里是 `main/palette_table.c`
- 网页量化时只在这 48 个里挑

## 五、单色快刷（MonoFast）：完全不同的思路

### 不是传位图，是传「跳变码」

```c
code = 2 * 上一帧 + 这一帧     // 每像素 2 bit
```

**面板只驱动状态变了的像素** —— 没变的不动 → 快，而且**不闪**。

### 线路格式：也是 4bpp，但只用低 2 位

```
每个像素一个 4bit 半字节：
    偶数像素  -> 高半字节（码在 bit5:4）
    奇数像素  -> 低半字节（码在 bit1:0）
    一行 720 像素 × 4 bit = 360 字节
```

**⚠️ 高 2 位是空着的** —— 见第七节。

### 编码：查表，不要逐位移位

一个字节（8 像素）的编码是纯函数 `(上一帧字节, 位图字节) → 4 个输出字节`，
而且 `old` 位只来自上一帧、`new` 位只来自位图 —— 所以**两张 256×4 的表**就够：

```c
输出[j] = TAB_P[prev][x] | TAB_S[src][x];
```

**实测：逐像素移位 ~75 ms，查表降到 ~14 ms。**

### 上一帧基准

驱动维护 `s_prev[43200]` 存**码位域**（1 = 白），不是位图。
清屏后面板实际是黑 → 初值全 0。更新时按字节取反即可（`prev[i] = ~src[i]`）。

## 六、三种模式对比

| | **ColorQual** | **ColorFast** | **MonoFast** |
|---|---|---|---|
| 状态数 | 64（48 有效） | 64（少一些） | **2** |
| 波形 | `qual_phase1/2/3` | `fast_color_phase1/2` | `mono_fast` |
| 相数 | 3 | 2 | 1 |
| 平面写入 | 2 次 | 2 次 | 0（跳变码） |
| 逻辑缓冲 | 345,600 B (8bpp) | 345,600 B | **43,200 B (1bpp)** |
| SPI 总量 | 518,400 B | 345,600 B | **172,800 B** |
| **实测耗时** | **~14.7 s** | **~8 s** | **~0.13 s** |
| 闪烁 | 有 | 有 | **无（差分）** |
| 适合 | 照片 | 图片预览 | **UI / 时钟 / 菜单** |

**线路层的帧大小完全一样（172,800 字节，都是 4bpp）** —— 差别在传几次、几个相位。

## 七、⚠️ 颜色是「波形」决定的，不是代码决定的

**这一条最容易误解。**

MonoFast 看起来"黑白"，**实际不是** —— 在我们这块 6 色屏上，
`mono_fast` 的两个状态落在 **黑 + 黄**。

因为波形表里的 LUT 决定「每个像素最终显影成什么颜色」。`mono_fast` 是
FrameFilm 按**黑白屏**做的，落到 6 色屏上终点色就变了。

> **同一份代码，换一张波形表就换颜色。**

### 想做彩色快刷？

| 路线 | 状态数 | 现实 |
|---|---|---|
| **直接用 ColorFast** | 64 | ✅ 现在就能用，8 秒 |
| 换 `mono_fast` 波形 → 任意 2 色 | 2 | ⚠️ 要自己造波形 |
| **用满 4bit → 8~16 态** | 8~16 | ⚠️ 要自己造波形 |

**第三条值得注意**：MonoFast 每个像素发 4 bit，但我们**只用了低 2 位**。
如果有一张自定义波形让 4 位都参与，理论上能到 16 态，而且是**单相快刷**。

**但我们的 9 张波形全是从 FrameFilm 逆向来的，造不了新的。**
所以"又快又彩色"目前卡在波形上 —— 和 7.3″ 遇到的是同一个瓶颈。

## 九、单色快刷的实测数据（`e6-mono-ui`）

| 优化项 | 帧耗时 |
|---|---|
| 初始（SPI 10 MHz + 逐像素编码） | 365 ms |
| → SPI 提到 40 MHz | 261 ms |
| → 20 行/事务（480→24 次） | 243 ms |
| → **查表编码** | **180 ms** |

```
编码 + SPI    49 ms   （SPI 理论下限 35 ms，编码已压到 ~14 ms）
面板刷新     131 ms   ← 硬地板，是波形本身的时长
────────────────────
合计         180 ms   ← 5.6 fps
```

**刷新耗时和「改了多少像素」有关**：

| 情况 | BUSY 时长 |
|---|---|
| 全屏都变 | 232 ms |
| 只改几个像素（时钟/状态栏） | **131 ms** |
