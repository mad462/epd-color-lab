# 调色迭代记录

> 这份文档记的是**调色这一路的思路和过程** —— 每一轮我基于什么假设、做了什么、
> 结果如何、得出了什么结论。重点是那些**被推翻的假设**，因为那才是真正推进的地方。
>
> 颜色怎么测、怎么评估的方法论在 [颜色方法论.md](颜色方法论.md)。
> 这份是"过程记录"，那份是"方法沉淀"。

---

## 起点

标称色板（FrameFilm 的设计值）跑出来的图**偏绿**。用户的原话是"之前偏绿"。

于是有了第一条主线：**实测色板**。

---

## 第一轮：标称 → 实测

**假设**：标称值是设计意图，和面板实际出的颜色差得远，换成实测值应该就好。

**做法**：固件加校准模式（开机直接进、串口输编号、整屏刷色），用仪器逐个测 52 个编号，
导出 `palette_qual_measured.csv`，三处（网页 `.act` / 私有 `.act` / 固件表）同步。

**结果**：偏绿**解决了** ✓，但**整体偏暗**。

**结论与数据**：

```
实测明度范围    L* 30.9 ~ 72.1   （只有 41 个单位，照片有 100）
实测平均色度    C* 19.6          （标称是 40.0，只剩 49%）
面板档位分布    30~40 有 19 个，60~70 只有 6 个，70~80 只有 1 个
```

**两个重要认识**：
1. 标称值不靠谱（高估亮度和饱和度），但**实测值也没好到哪去** —— 见后面的测量偏差
2. **面板的物理范围天生就窄**，这是后面所有问题的总根源

---

## 第二轮：加自动色阶 → 过曝

**假设**：面板最亮只到 L\*72，忠实映射必然偏暗，得把画面的明暗范围拉满。

**做法**：加「自动色阶」—— 取亮度直方图 2%~98% 分位，映射到 0~255。

**结果**：**白色部分过曝**，整体对比度偏高。

**结论**：自动色阶把范围拉到 255，**更多像素挤到"面板最亮那一档"**上 ——
面板 L\*72 以上没有档位，所以 L\*72~100 的内容全堆在一个档位 → 一片死白。

**改动**：
- 分位改到 1%~99%（别拉那么狠）
- 输出范围从 `0~255` 改成 `8~247`（两头留余量）

---

## 第三轮：面板范围映射 → 发灰发黄（**方向对，实现错**）

**假设**：既然问题是"高光挤成一档"，那把图像的明度**整体压进面板范围**就好了。

**做法**：加了「映射到面板范围」—— 把图像 L\* 从 0~100 线性压到面板的 30.9~72.1，
色度按 `k = L2/L` 缩放。

**结果**：**发灰 + 发黄**。

**推翻它的数据**：同条件渲染对比（都用实测色渲染 = 面板真实显示）：

| 设置 | 结果 |
|---|---|
| 映射 **ON** | 惨白、发灰橙、对比度低 |
| 映射 **OFF** | 颜色明显更浓、对比更好 |

**当时的结论（错的）**：这个功能没用，关掉。

**后来的修正**：**错在实现，不在想法**。三处问题：
1. 全压（没有 strength 混合）
2. **饱和色也一起压了** —— 这是发灰发黄的直接原因
3. 动了 a/b（按 L2/L 缩色度）—— 引入色偏

详见「第八轮」。

## 第四轮：明度权重 2 → 1.2

**背景**：发灰发黄之外，用户还报"**肤色变黄、少了红润**"。

**做法**：把量化器的明度权重从 FrameFilm 的 2 降到 1.2。

**为什么**：权重 2 意味着**几乎只看明暗、放弃色相**。实测：

```
源肤色 #D6A082  (L*70.2 a*+16.2 b*+23.5)  健康红润
  权重 2.0 -> 索引15 #ABB3AB (L*72.1 a* -4.3)   同明度的浅灰绿，红润全丢
  权重 1.2 -> 索引47 #937670 (L*64.5 a*+10.3)   暖色保住 ✓
  权重 0.8 -> 索引39 #9C5D4E (L*46.2 a*+24.1)   红润回来 ✓

中性灰 L*45:
  权重 2.0 -> #695E52 (b*+8.5 偏黄)
  权重 1.2 -> #585D57 (b*+2.8 基本中性) ✓
```

**结论**：明度权重 1.2 成了新默认值。**这个数字是量出来的，不是拍的。**

## 第五轮：全局曲线压高光 → 暗部被一起压暗

**用户原话**：*"我去压高光的时候，会把暗区也压暗掉"*

**原因**：我那条全局曲线的拐点是 `k = 255*(1-0.7*hs)` —— `hs=100%` 时 **k 只有 76**，
那早就不是"高光"了，**偏暗的中间调全被卷进去**。

**更根本的问题**：一条全局曲线没法区分「这个像素暗是因为它在阴影里」
和「它本来就是个暗色物体」。

**做法**：换成 **Photoshop「阴影/高光」风格的局部算法** ——
先求一张大半径模糊的亮度图当作"这一带有多亮"，再用它做蒙版：

```
阴影蒙版 = (1 - 局部亮度)² × (1 - 该像素亮度)     // 只作用在"暗的地方的暗像素"
高光蒙版 = 局部亮度²       × 该像素亮度            // 只作用在"亮的地方的亮像素"
```

**验证**（合成图：左半暗 40 / 右半亮 215）：

| 操作 | 暗区 | 亮区 |
|---|---:|---:|
| 原始 | 40.0 | 215.0 |
| **高光 +100** | **39.8**（几乎不动 ✓） | 165.1 |
| **阴影 +100** | 58.4 | **216.8**（几乎不动 ✓） |

**顺带的教训**：系数也不能拍。第一版用 1.6，白区被乘到 0.04（215 → 37），
那是毁图不是压高光。最终用 `1 + s·mShadow·0.9 − h·mHigh·0.45`。

## 第六轮：控件的自我克制

**用户原话**：*"现在挺难调的 选项太多，变量太多，感觉怎么调都调不好"*

**这是我的设计失误** —— 一路上每个问题加一个旋钮，加到了 **10 个滑杆**，还互相牵连。

**做法**：
- 默认只留 **6 个**：色板 / 抖动 / 构图尺寸 / 亮度 / 对比度 / 饱和度
- 其余 9 个收进「**高级**」
- 加 **4 个预设**：标准 / 提亮 / 浓一点 / 救高光
- **黑点改成自动跟随色板**（它是面板属性，不是画面属性，本来就不该手动调）

**黑点自动的验算**：

```
实测色板   最暗 L*30.9 -> 自动算出 73   （实测最暗色 #454951 的 R=69，对得上 ✓）
去污染色板 最暗 L*13.0 -> 自动算出 34   （之前手动建议 20~30，也对得上 ✓）
```

## 第七轮：测量偏差 —— **这是最深的一条线**

**起因**：调来调去总觉得不对，问了一句"是不是颜色没测准导致的"。

### 7.1 先看症状

用户报"偏黄"，但一算平均色偏：

```
实测 w2 无映射:   dL* -4.8   da* -7.3   db* -1.5
```

**b\* 是 -1.5（偏蓝！），根本不黄。但 a\* 掉了 7.3 —— 红色大幅丢失。**

红色丢了、黄色还在 → 暖色从"橙红"被读成"黄"。

**教训：症状描述 ≠ 物理量。** 用户说"偏黄"，物理上可能是"红色丢了"。

### 7.2 三条独立证据指向同一个原因

**证据一：数据拟合**

```
实测_线性 = 0.429 · 标称_线性 + 0.073
残差 RMS = 0.0244
```

那个 `+0.073` 是杂散项 —— 面板显示纯黑时仪器也读到约 76/255。

**证据二：仪器规格**

用户用的 **林上 LS173** 规格写明：**`D/8，包含镜面反射光（SCI）`**。

`SCI` 把面板保护膜的镜面反射也算进读数 —— 这部分和底下的颜色无关，
等于给每个读数加了一份白光。**后果正是暗部被抬起、色度被稀释。**

同系列里 LS175 / LS172 用的是 `45/0` 几何（镜面反射从 45° 出去、进不到接收器），
那才是合适的工具。

**证据三：第三方独立实测色板**

[epdoptimize](https://github.com/paperlesspaper/epdoptimize) 提供了 **4 套独立测量的
Spectra 6 色板**（不同人、不同仪器、不同面板批次）：

```
黑：我们 L*30.9  |  他们 L* 13 / 1 / 11 / 13     ← 四套一致：我们太亮
白：我们 L*72.1  |  他们 L* 79 / 80 / 92 / 86    ← 四套一致：我们太暗
```

**四套全部同意"我们的测量被压缩了"。**

### 7.3 但不能用来精确定标

我试着拿他们的值当锚点拟合校正，**两次都失败**，值得记下来：

| 尝试 | 结果 |
|---|---|
| 用全部 6 色拟合 | 参照之间分歧太大（红的 L\* 跨 23~55，比要测的偏差还大）→ 拟合出的是"参照之间的分歧"，b 变负数、对比度反降到 3:1 ✗ |
| 只用黑白两端拟合 | 过度外推：推出**白反射率 61%**（电子纸不可能）、对比度 **37:1**（同类规格 15~22）✗ |

> 途中还犯了个错：把拟合方向用反了（`真实 = a·实测 + b` 当成 `实测 = a·真实 + b` 再取逆），
> 结果荒谬（b = -10%）。修正后锚点自检才通过（白色预测 `#CAD5CA` vs 他们 `#CACFD0`）。

**最终结论：物理边界校正（b = 5.1%）是最佳估计。**

它同时满足两个互相独立的约束：

| 约束 | 物理边界校正 | 锚点拟合 |
|---|---|---|
| 对比度落在同类面板规格 15~22 | **19.7 : 1** ✓ | 37 : 1 ✗ |
| 白反射率落在电子纸常见 30~40% | **37%** ✓ | 61% ✗ |

## 第八轮：参考 epdoptimize 重做

看完 epdoptimize（Apache-2.0）之后做了三件事。

### 8.1 「映射到面板范围」重做 —— 修掉了第三轮放弃它的真正原因

他们和我那版的**三点关键差别**：

```js
// ① strength 混合 —— 不是全压，是压一部分
const targetL = sourceL + (compressedL - sourceL) * effectiveStrength;

// ② 饱和度保护 —— 颜色越饱和，压得越轻（最多减 85%）
const effectiveStrength = strength * (1.0 - getDynamicRangeChromaProtection(r,g,b));

// ③ 压完自检 —— 掉太多饱和度就二分法把 strength 降下来（5 步）
if (!isProtectedChromaFit(...)) { /* 二分搜索 */ }
```

**饱和度保护实测效果**：

```
中性灰 #808080  饱和 0.00  保护 0.00  有效 strength 1.00   ← 全压
肤色   #d6a082  饱和 0.39  保护 0.33  有效 strength 0.67
饱和红 #c82828  饱和 0.80  保护 0.85  有效 strength 0.15   ← 几乎不压
```

**这就是关键**：我当初全压，把饱和色也压了 → 发灰发黄。
现在**只压中性色、放过饱和色**。UI 也从复选框改成 **0~100 的滑杆**。

另外他们**不动 a/b**，我上一版按 `L2/L` 缩色度是错的。

### 8.2 误差扩散加蛇形扫描

奇数行反向扫描并把核的 `dx` 取反。误差扩散的方向性伪影（斜纹/蠕虫）
主要来自"每行都朝同一个方向推误差"，交替方向能明显打散。

## 三条贯穿始终的教训

### ① 平均色差小 ≠ 观感好

ΔE2000 说"白平衡方案最好"（适应后 5.98），上屏却明显偏暗 ——
**平均值掩盖了全局明度偏移**。

### ② 症状描述 ≠ 物理量

用户说"偏黄"，量出来 b\* 是 **-1.5（偏蓝）**，真问题是 **a\* 掉了 7.3（红润丢失）**。

**必须拆开 Lab 分量 + 渲染出来看。**

### ③ 渲染出来亲眼看，比算指标有效得多

```
用**实测色板**渲染量化结果（不是用标称值渲染！）
  —— 标称值渲染出来的是"理想效果"，会骗人；
     实测值渲染出来的才是"上屏后眼睛看到什么"
```

这个方法改变了整个排查效率。之前几轮靠猜机制、算指标，收效甚微；
改成渲染出来看之后，一轮就定位到"面板映射导致偏黄"。

## 当前的完整管线

```
原图
 ├─ ① 自动色阶（默认开）      1%~99% 分位 -> [黑点, 247]
 ├─ ② 黑点（自动跟随色板）    面板最暗档位的 L* -> 中性灰 sRGB
 ├─ ③ 动态范围压缩（默认关）  strength 滑杆 + 饱和度保护 + 二分自检
 ├─ ④ 局部阴影 / 高光         PS 风格，暗部亮部互不干扰
 ├─ ⑤ 饱和度 / 色偏微调       Lab 里缩放 a,b + 偏移 b*
 └─ ⑥ 最近色匹配 + 误差扩散抖动
      度量 CIE Lab（明度权重 1.2）· 蛇形扫描 · 色板 = 实测值
```

**默认只露 6 个控件 + 4 个预设，其余收进「高级」。**

## 遗留问题

### 1. 测量偏差还没真正解决

我们知道仪器几何是错的（D/8 SCI），也知道偏差量级约 5%，
但**这是推出来的，不是测出来的**。真正的解决只有两条路：

- 换 `45/0` 几何的仪器重测（林上 LS172，约 ¥980）
- 确认面板对比度后，用物理边界精确反推

**验证方法（30 秒）**：全屏刷白和黑，算对比度。
是 **15~22:1** 就说明诊断成立；还是 6:1 就说明诊断错了。

### 2. 面板的结构性限制改不了

```
L*40~52 之间没有任何中性档位  -> 中间调必然被染上一点色
L*60 以上只有 7 个档位        -> 亮部渐变必然分层
动态范围只有 41 个 L* 单位    -> 高光和暗部只能"舍一头"
```

**继续找"那个完美的设置"会一直找不到** —— 这些不是参数能解决的。

### 3. 2 相色板还没实测

`palette_fast.csv` 目前还是标称值。2 相用完全不同的波形，颜色和 3 相不是一套值。

### 4. 量化是在补偿一个测量误差

在色板校准之前，**所有调参都在跟测量偏差搏斗**。这是"怎么调都不对"最可能的原因。
