# mono-ui —— 单色快刷（MonoFast）调研

> **状态：调研阶段完成，UI 实现待做。**
> 这份文档是给"以后回来接着做"用的 —— 结论、踩过的坑、下一步都在这里。

仓库 [epd-color-lab](../README.md) 的子项目：同样这块屏（兴泰 EPD037A02 / JD7601 级，
720×480 六色）上的**黑白差分快刷**。

**和 48 色是两个独立工程**，共享 `epd370.c` / `waveforms.c`，但互不影响。
48 色那个在**仓库根目录**（`..`）。

## 一、结论先说

| 项目 | 结果 |
|---|---|
| **能不能用** | ✅ 能用，画面正确 |
| **刷一帧** | **180 ms** |
| **帧率上限** | **5.6 fps** |
| 对比 48 色 | **94 倍快**（17 s） |
| Flash 占用 | 1.6%（270 KB） |
| **颜色** | ⚠️ **只有 2 色：黑 + 黄**（不是黑白，见第三节） |

**做 UI（时钟、菜单、状态栏）完全够用。**

## 二、原理：不是传位图，是传「跳变码」

做法来自 FrameFilm 的 `hal_epd_370_ark.c`。

```c
code = 2 * 上一帧 + 这一帧      // 每像素 2 bit
```

**面板只驱动状态变了的像素** —— 没变的不动 → 快，而且**不闪**。

### 线路格式

```
每个像素一个 4bit 半字节：
    偶数像素 -> 高半字节（码在 bit5:4）
    奇数像素 -> 低半字节（码在 bit1:0）
一行 720 像素 × 4 bit = 360 字节
一帧 360 × 480        = 172800 字节
```

### 编码约定（FrameFilm 实测得出）

| 项 | 值 |
|---|---|
| 码位极性 | `1 = 白`、`0 = 黑`（**和位图相反**，位图 `1 = 黑`） |
| 清屏后面板状态 | 黑 → 上一帧初值全 `0` |
| 位图字节序 | MSB 在前（代码里按像素取位，不用额外反序） |

驱动维护 `s_prev[43200]` 存**码位域**（不是位图），更新时按字节取反即可。

## 三、⚠️ 最重要的一条：颜色是「波形」决定的

**这块屏上 MonoFast 的两个状态是「黑 + 黄」，不是黑白。**

因为波形表里的 LUT 决定「每个像素最终显影成什么颜色」。`mono_fast` 是
FrameFilm 按**黑白屏**做的，落到我们这块 6 色屏上终点色就变了。

> **同一份代码，换一张波形表就换颜色。**
> 颜色不是代码能调的参数。

### 想做彩色快刷？

| 路线 | 状态数 | 现实 |
|---|---|---|
| 直接用 **ColorFast** | 64 | ✅ 现在就能用，约 9 s |
| 换 `mono_fast` 波形 → 任意 2 色 | 2 | ⚠️ 要自己造波形 |
| **用满 4bit → 8~16 态** | 8~16 | ⚠️ 要自己造波形 |

**第三条值得注意**：MonoFast 每像素发 **4 bit**，但**只用了低 2 位**。高 2 位空着。
如果有一张自定义波形让 4 位都参与，理论上能到 16 态的单相快刷。

**但 9 张波形全是从 FrameFilm 逆向来的，造不了新的** —— 和 7.3″ 那块屏是同一个瓶颈。

### 一条没试过的便宜实验

**拿其它 8 张波形当 mono 波形用**（改一行代码），看各给出什么颜色和耗时：

| 候选 | 说明 |
|---|---|
| `wf_mono_clear` | 另一组 2 色 |
| `wf_fast_color_phase1` | 可能是彩色的 2 态 |
| `wf_qual_phase1` | 同上 |
| `wf_restore_after_fast_color` | ? |

⚠️ 换波形后**时长会变** —— `mono_fast` 短是因为它是差分波形。
`qual_phase1` 那种全屏显影的可能要 **5 秒**。

## 四、优化过程（实测）

| 步骤 | 帧耗时 | 省 |
|---|---|---|
| 初始（SPI 10 MHz + 逐像素移位） | 365 ms | — |
| → SPI 提到 **40 MHz** | 261 ms | −104 ms |
| → **20 行/事务**（480 次 → 24 次） | 243 ms | −18 ms |
| → **查表编码** | **180 ms** | **−63 ms** |

### 最终分解

```
编码 + SPI    49 ms   （SPI 理论下限 35 ms，编码已压到 ~14 ms）
面板刷新     131 ms   ← 硬地板，是波形本身的时长
────────────────────
合计         180 ms   ← 5.6 fps
```

### 查表编码是最大的一笔

逐像素移位要 34.5 万次迭代（160 MHz 下每像素约 35 周期 → ~75 ms）。
但一个**字节**的编码是纯函数 `(上一帧字节, 位图字节) → 4 个输出字节`，
而且 `old` 位只来自上一帧、`new` 位只来自位图 —— 所以**两张 256×4 的表**就够了：

```c
输出[j] = TAB_P[prev][x] | TAB_S[src][x];
```

每字节从 8 轮移位变成 2 次查表 + 4 次或 → **编码 ~75 ms 降到 ~14 ms**。

### 试过但**没用**的

| 尝试 | 结果 |
|---|---|
| 缓冲从 PSRAM 移到内部 RAM | 110 → 110 ms（不是访存瓶颈） |
| 加 `-O2` | 110 → 110 ms |
| 20 行/事务 | 只省 18 ms（不是事务开销） |

**最后是算法层面的改动才解决** —— 说明当时那 110 ms 真的是 CPU 在算。

### 附带发现：刷新耗时和「改了多少像素」有关

| 情况 | BUSY 时长 |
|---|---|
| 全屏都变 | 232 ms |
| 只改几个像素（时钟/状态栏） | **131 ms** |

## 五、踩过的坑

| 现象 | 根因 | 修法 |
|---|---|---|
| **每次刷完就重启**（`LoadProhibited`，`EXCVADDR=0x1111116b`） | `line[]` 声明成 `MONO_STRIDE/2`（**45** 字节），但一行要 **360** 字节 → 写爆 8 倍，踩烂邻接内存 | 加了明确的宏 `MONO_LINE_BYTES (MONO_W*4/8)`，注释里写了"别写成 STRIDE/2" |

> 定位方法：串口抓到 `Guru Meditation` + 调用栈，用 `xtensa-esp32s3-elf-addr2line`
> 解出 `mono.c:251`。**PlatformIO 的 `monitor_filters = esp32_exception_decoder` 也能自动解。**

## 六、代码结构

```
main/
  main.c        演示：七段大数字 + 进度条 + 边框
  mono.c/.h     单色层
                  - 帧缓冲 43200 字节（1bpp）
                  - 绘制原语：pixel / hline / vline / fill / rect
                  - 七段数字 mono_digit_seg()（缩放自由，不用字库）
                  - 5x7 点阵 ASCII mono_text5x7()
                  - 查表差分编码 + push_frame()
                  - 会话模式 mono_session_begin/end()（帧间保持上电）
  epd370.c/.h   面板驱动（比 48 色那份多了 DTM1 流式 + bulk 写入）
  waveforms.c   9 张波形表（含 mono_fast / mono_clear）
```

**和 48 色的 `epd370.c` 的区别**：这里多了 `epd370_dtm1_begin/row/bulk/end`，
SPI 也从 10 MHz 提到了 **40 MHz**。

## 七、下一步（做 UI 时从这里开始）

### 1. 先补一个模式切换

`单色 UI 常驻 → 点开看图切 48 色 → 看完切回来`。

⚠️ **不能直接切** —— FrameFilm 里有专门的过渡流程（`epd_spectra_prepare()`），
跨模式要用过渡波形，否则花屏。现成的有 `wf_restore_after_fast_color`。

### 2. 再补 UI 组件

- **中文字库** —— 现在只有 5x7 英文/数字。中文要 12x12 或 16x16 点阵
- **常用控件** —— 状态栏、列表、进度条、按钮反馈
- **局部刷新** —— 现在每次都推整帧 172800 字节。如果能只推变化的行，
  配合面板本来就有的"改得少就刷得快"特性，可以做得很流畅

### 3. （可选）把 40 MHz 的改进也带给 48 色

48 色工程还在 10 MHz。既然 40 MHz 已经验证稳定，
**能省掉相位间推平面的 ~1.4 秒**（17 s → ~15.6 s）。

## 八、怎么跑

```bash
cd mono-ui        # 或从仓库根目录 pio run -d mono-ui
pio run -t upload
pio device monitor          # 看每帧耗时
```

**接线和 48 色完全一样**：`BUSY=42 CS=41 DC=40 RST=39 SDA=38 SCL=47`

预期画面：

```
┌──────────────────────────────────────┐
│  MONO FAST                           │

│  N=12                   ┌──────────┐ │

└──────────────────────────────────────┘
```

串口每帧打一行：`count=12  帧耗时 180 ms` + `分段时间：编码+SPI 49 ms  刷新 131 ms`

## 九、和 48 色的数据关系

| | 48 色 | 单色 |
|---|---|---|
| 逻辑缓冲 | 345,600 B（8bpp） | **43,200 B（1bpp）** |
| 线路帧 | 172,800 B（4bpp 平面） | 172,800 B（4bpp 跳变码） |
| 一次显示传几次 | **3 次** | **1 次** |
| SPI 总量 | 518,400 B | 172,800 B |
| 耗时 | **17 s** | **0.18 s** |

**线路帧大小完全一样，差别在传几次、几个相位。**

详细的数据格式见 [`../docs/数据格式.md`](../docs/数据格式.md)。
